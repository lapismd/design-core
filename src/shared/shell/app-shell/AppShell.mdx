# App Shell

`@lapismd/design-core/shell` is a bounded structural layout for applications that own
their navigation and content. Consumers compose its compound parts once; the
root presents them as independently collapsible and resizable desktop sidebars
or as a container-aware mobile track.

Start with **Shell/Guidance** for the canonical compound topology, toggle
placement, cross-column header alignment, collapsed-rail content rules, and
desktop preview overlays (`previewOnHover` / `revealOnEdgeHover`). This page
is the detailed API and behavior reference.

## Structure

{/* prettier-ignore */}
```tsx
<AppShell.Root {controller} displayMode="auto" mobileBreakpoint={1024}>
  <AppShell.Sidebar side="left">
    <AppShell.Sidebar.Header>...</AppShell.Sidebar.Header>
    <AppShell.Sidebar.Body>...</AppShell.Sidebar.Body>
    <AppShell.Sidebar.Footer>...</AppShell.Sidebar.Footer>
  </AppShell.Sidebar>
  <AppShell.Main>
    <AppShell.Toolbar>
      <AppShell.Sidebar.Toggle side="left" />
      ...
      <AppShell.Sidebar.Toggle side="right" />
    </AppShell.Toolbar>
    <AppShell.Body>...</AppShell.Body>
  </AppShell.Main>
  <AppShell.Sidebar side="right" closeable>
    <AppShell.Sidebar.Header>
      ...
      <AppShell.Sidebar.Close />
    </AppShell.Sidebar.Header>
    <AppShell.Sidebar.Body>...</AppShell.Sidebar.Body>
  </AppShell.Sidebar>
</AppShell.Root>
```

Every part is optional except `Root`. Omitting either sidebar leaves the main
column to fill the available bounded container. `displayMode` defaults to
`"auto"` and resolves from the root's own observed width, switching below the
default `mobileBreakpoint={1024}`. Use `"desktop"` or `"mobile"` for an
explicit, reactive presentation without duplicating the child composition.
Stories that test one layout pin that mode; application demos may expose all
three values as ordinary programmatic state.

For document-local navigation, switch the body to independently scrolling
regions and mount a consumer-controlled sidebar on either side:

{/* prettier-ignore */}
```tsx
<AppShell.Body layout="regions" label="Markdown document">
  <AppShell.Body.Toggle
    side="left"
    target="document-contents"
    pressed={tableOfContentsSide === "left"}
    onclick={() => toggleTableOfContents("left")}
  />
  <AppShell.Body.Toggle
    side="right"
    target="document-contents"
    pressed={tableOfContentsSide === "right"}
    onclick={() => toggleTableOfContents("right")}
  />

  <AppShell.Body.Sidebar
    panelId="document-contents"
    mobileLabel="Document contents"
    side={tableOfContentsSide ?? "right"}
    bind:open={tableOfContentsOpen}
    label="Table of contents"
  >
    ...
  </AppShell.Body.Sidebar>

  <AppShell.Body.Content label="README content">
    <article>...</article>
  </AppShell.Body.Content>
</AppShell.Body>
```

The default `layout="scroll"` remains the compact one-region body. In
`layout="regions"`, every `Body.Sidebar` and `Body.Content` installs its own
shadcn Scroll Area. The body itself remains fixed and non-scrolling, and the
consumer owns the local sidebar's `open` value and which side it occupies.
This makes table-of-contents state easy to derive from a selected Markdown file
without registering another application-level sidebar.

`Body.Toggle` is an icon-sized shadcn Button positioned inside the body:
top-left for `side="left"` and top-right for `side="right"`. It exposes
`aria-pressed`; consumers pass `pressed`, an accessible `label` when the
defaults are not specific enough, and their own click handler. A `target`
connects it to a mounted `Body.Sidebar` for mobile presentation. The toggle
remains mounted when its desktop sidebar closes, so focus is retained and the
body reclaims the sidebar width.

## Mobile presentation

Mobile mode keeps one composition and presents it as left, main, and right
stages. Outer sidebars and registered body sidebars join the matching edge
lane. When an edge has more than one panel, an internal shadcn Select chooses
the active one using `mobileLabel` (or the accessible `label` by default).

`Sidebar.Toggle` reveals its mobile panel and `Sidebar.Close` returns to main
without changing persisted desktop collapse, closed, or width values.
`Body.Toggle` reveals its `target`. A horizontal swipe from main reveals an
available edge; swiping toward main, tapping the exposed stage, or pressing
Escape dismisses it. Vertical intent, interactive controls, and genuine
horizontal scrollers retain their native interaction. Offstage lanes are
`inert` and `aria-hidden`, and button-triggered dismissal restores focus to the
opening control.

`controller.mobile` exposes transient `resolvedMode`, `stage`,
`activeLeftPanelId`, and `activeRightPanelId`, plus `show()`, `showMain()`, and
`selectPanel()`. This state is presentation-only and never appears in layout
snapshots:

```ts
shell.mobile.show("left", "projects");
shell.mobile.selectPanel("right", "document-contents");
shell.mobile.showMain();
```

Repeated outer sidebars must use a controller created with
`shell.createSidebar(id, side)` so mobile mode has a stable panel identity.

## Constrained desktop presentation

Desktop keeps the main stage usable before allowing inline sidebars to consume
all available width. Its protected width comes from
`--ui-shell-desktop-min-main-width` (`36rem`) or the
`desktopMinMainWidth` root prop. When the bounded root cannot fit that stage,
the shell removes outer panels from inline flow in this order: right sidebar,
named outer-left sidebars, then the built-in left sidebar. Their existing
toggle or edge action opens a temporary full-height overlay preview
(`data-desktop-overlay-preview`), not a Popover and not collapsed/closed
`previewOnHover`. See **Complete shell composition** and **Constrained
desktop overlays**.

This is presentation-only. Collapsed, closed, and resized controller values
remain unchanged, and the same panels return inline when the container grows.
It is distinct from mobile mode: the desktop toolbar, body geometry, hover
previews, and resize affordances remain available.

`Main` is an inset, bordered surface while both sidebars remain full height.
The shell containers use `overflow: hidden`; the default `AppShell.Body`,
each body region, and every `AppShell.Sidebar.Body` install their own shadcn
Scroll Area and vertical scrollbar. The main toolbar and each sidebar header
and footer therefore remain fixed while content regions scroll independently.
A collapsed sidebar
keeps the same scrollable viewport for its icon rail but hides the scrollbar.
Its inline header and footer separators are also removed; a temporary expanded
overlay restores consumer separators that remain defined. Outer / first project
sidebar headers should omit `border-block-end` entirely (see
**Shell/Guidance**). Built-in `Sidebar.Toggle` and `Sidebar.Close` actions in
a collapsed header share the main toolbar's vertical action baseline.

Expanded sidebars include an accessible resize slider by default. Pointer
dragging follows the sidebar edge; arrow keys move it by 16px, Shift+Arrow by
32px, and Home/End move to the configured bounds. Set `resizable={false}` on a
sidebar to omit its handle.

Pass `sidebarController` to `Sidebar` or `Sidebar.Toggle` when a layout needs
more than one independently controlled surface on the same side. Create a named
panel through the root controller when its state should participate in layout
persistence:

{/* prettier-ignore */}
```tsx
<script lang="ts">
  const shell = new AppShellController();
  const projectSidebar = shell.createSidebar("projects", "left");
</script>

<AppShell.Sidebar
  side="left"
  sidebarController={projectSidebar}
  variant="outer"
  closeable
  revealOnEdgeHover
>
  ...
</AppShell.Sidebar>

<AppShell.Sidebar side="left">
  <AppShell.Sidebar.Header>
    <AppShell.Sidebar.Toggle side="left" sidebarController={projectSidebar} />
    ...
  </AppShell.Sidebar.Header>
  ...
</AppShell.Sidebar>
```

`variant="outer"` paints a full-height bounded surface. When
`revealOnEdgeHover` is enabled, collapsing or closing that sidebar installs a
narrow page-edge control. Pointer hover or keyboard focus previews the sidebar
as an overlay without moving the rail, file sidebar, or main column; clicking
the edge control expands it inline. The same accessible resize handle remains
available on the preview, and its controller width is retained when the sidebar
next opens inline. This is a desktop affordance, not the Workspace mobile sheet.

`Sidebar.Toggle` is the shared toolbar action for either side. It collapses an
expanded sidebar, expands a collapsed sidebar, and opens a closed sidebar.
Set `previewOnHover` when a toggle in adjacent chrome should preview its
collapsed or closed sidebar as an expanded overlay. The default 600ms opening
delay is configurable with `previewDelay`; leaving before it elapses cancels the
preview, and moving into the overlay keeps it open without moving adjacent
columns. Overlay width always resolves from the expanded sidebar width even
when the retained controller state is collapsed. Portalled popup content also
counts as part of the preview while it is linked through `aria-controls` or
`aria-owns`, or is opened by an accessible `combobox`/`aria-haspopup` trigger
inside the sidebar. This lets Select, Popover, and menu options remain
interactive without pinning the sidebar open permanently.
`closeable` enables a nested `Sidebar.Close` action. Put that action in
`Sidebar.Header`; its automatic inline margin places it at the far edge. Closing
removes the sidebar from layout completely so `Main` reclaims its width and
gap. Collapsing still preserves the icon rail.

## Controller

Create one `AppShellController` per shell. `controller.left` and
`controller.right` expose `collapsed`, `state`, `setCollapsed()`, `expand()`,
`collapse()`, `toggle()`, `closed`, `setClosed()`, `open()`, `close()`, `width`,
`setWidth()`, `resizeBy()`, and `resetWidth()`. `state` is `"expanded"`,
`"collapsed"`, or `"closed"`. Widths clamp to 220–520px by default; configure
shared bounds with `sidebarMinWidth` and `sidebarMaxWidth`. `useAppShell()` gives
consumer components access to the nearest root controller without installing
global application state.

The transient `previewed` state is managed through `schedulePreview()`,
`schedulePreviewDismiss()`, `keepPreview()`, and `dismissPreview()`. It does not
change `state`, so an expanded overlay can preview a collapsed rail without
changing consumer-owned collapse state or adjacent geometry.

`controller.mobile` is an `AppShellMobileController`. It is deliberately
excluded from `AppShellLayoutV1`; switching between desktop and mobile restores
the exact durable sidebar geometry that was present before the mode change.

Collapsed sidebars remain mounted as persistent icon rails. Consumer controls
should retain accessible names when their visible labels are omitted.

## Layout persistence

Inject an `AppShellLayoutPersistence` adapter to restore and automatically save
the durable state of every registered panel: `collapsed`, `closed`, and its
explicit expanded `width`. The package includes a JSON `localStorage` adapter:

```ts
import {
  AppShellController,
  createLocalStorageAppShellLayoutPersistence,
} from "@lapismd/design-core/shell";

const shell = new AppShellController({
  persistence: createLocalStorageAppShellLayoutPersistence(
    "cv-studio.app-shell",
  ),
  saveDebounceMs: 200,
});

const projects = shell.createSidebar("projects", "left");
```

`AppShell.Root` calls `restoreLayout()` when it mounts and flushes a pending
save when it unmounts. Controller-only hosts may call `restoreLayout()` and
`flushSave()` directly. The serialized `AppShellLayoutV1` is versioned and
JSON-safe; invalid panels and saved side mismatches are ignored, while restored
widths are clamped to the receiving controller's bounds.

The local adapter defaults to the
`@lapismd/design-core/app-shell-layout` storage key when no key is supplied. Applications
with multiple shells should provide a stable application-specific key. A custom
adapter may save to desktop settings, a database, or another host-owned store
without changing shell components.

## Tokens

| Token                                       | Default                | Purpose                                     |
| ------------------------------------------- | ---------------------- | ------------------------------------------- |
| `--ui-shell-height`                         | `100vh`                | Root application height                     |
| `--ui-shell-left-sidebar-width`             | `18rem`                | Expanded left sidebar                       |
| `--ui-shell-right-sidebar-width`            | `18rem`                | Expanded right sidebar                      |
| `--ui-shell-right-sidebar-gap`              | `0.5rem`               | Gap before right sidebar                    |
| `--ui-shell-collapsed-sidebar-width`        | `3rem`                 | Either collapsed icon rail                  |
| `--ui-shell-body-sidebar-width`             | `14rem`                | Local body sidebar width                    |
| `--ui-shell-mobile-sidebar-width`           | `min(22rem, 86cqw)`    | Mobile edge lane width                      |
| `--ui-shell-desktop-min-main-width`         | `36rem`                | Protected desktop main width                |
| `--ui-shell-sidebar-toggle-indicator-width` | `24%`                  | Expanded toggle panel mark                  |
| `--ui-shell-toolbar-height`                 | `3rem`                 | Top chrome divider baseline                 |
| `--ui-shell-main-block-inset`               | `0.5rem`               | Desktop main top/bottom inset (0 on mobile) |
| `--ui-shell-main-radius`                    | `0.875rem`             | Main surface radius                         |
| `--ui-shell-main-shadow`                    | `shadow-sm` equivalent | Main surface depth                          |

Override tokens on `:root` or the shell root. Colors continue to come from the
shared semantic theme. Left and right width tokens remain authoritative until
the corresponding controller receives an explicit resize or restores one
through its layout adapter. When no inline right shell sidebar is mounted, the
main surface also uses the block inset at its trailing edge, keeping its right
gap equal to its bottom gap. Body-local sidebars do not suppress this outer
spacing.

## Shell or Workspace?

Choose `@lapismd/design-core/shell` for structural application chrome with
consumer-owned content. Choose `@lapismd/design-core/workspace` when the application
needs registered views, tabs, recursive splits, general workspace persistence,
commands, settings, plugins, windows, or general-purpose overlays. Both can
present mobile navigation, but Shell remains a small geometry/controller layer;
Workspace owns the full view lifecycle. Shell persistence is intentionally
limited to desktop sidebar geometry.
