# Workspace

The Workspace layer provides a reusable application shell with recursive tabs
and splits, sidebars, floating windows, mobile presentation, settings,
commands, static plugins, and controller-owned persistence.

## Boundary

Workspace is a framework, not an application. Consumers provide views,
resources, persistence adapters, commands, and statically configured plugins.
The layer does not own routes, filesystems, vaults, editors, or dynamic plugin
discovery.

## Imports

```ts
import {
  AppShell,
  AppShellController,
  WorkspaceView,
} from "@lapismd/design-core/workspace";

import { WorkspaceCommandPalette } from "@lapismd/design-core/workspace/command-palette";
import { WorkspacePopoutSurface } from "@lapismd/design-core/workspace/popout";
import { WorkspaceTabs } from "@lapismd/design-core/workspace/tabs";
import {
  WorkspaceProblems,
  problemsPlugin,
} from "@lapismd/design-core/workspace/problems";
```

Every top-level Workspace component family with a public barrel has a matching
package subpath. Optional plugins are available from
`@lapismd/design-core/workspace/plugins/fmode` and
`@lapismd/design-core/workspace/plugins/notifications`.

## Panels

`Workspace/Panels/Explorer` is a controller-driven file/folder presentation
family (`@lapismd/design-core/workspace/explorer`). It owns tree chrome,
selection, menus, and HTML5 file-move affordances. Consumers inject tree/action
adapters for vault listing, create/rename/delete, active-file sync, and
preferences. Native OS path actions and Lapis-specific URLs stay on the host
via `buildItemMenu`. Layout tab drag-and-drop remains separate
(`WorkspaceDragState` / drop overlay).

`Workspace/Panels/Problems` is the application-independent diagnostics
presentation (`@lapismd/design-core/workspace/problems`). Applications and
plugins publish plain diagnostics through owner-isolated collections on
`AppShellController.diagnostics`; they keep resource URI interpretation,
navigation, code actions, editors, and language services in host adapters.
`problemsPlugin()` registers the movable view and quietly seeds a closed bottom
tab only when no persisted Problems leaf exists. Diagnostics are ephemeral and
must never be added to workspace layout persistence.

Registered views may contribute an optional structured badge through
`WorkspaceViewChrome`. Workspace tab, dock, grouped-panel, and mobile labels
render the badge beside the live view title while keeping `WorkspaceTab.title`
as the serialized fallback. Use this contract for ephemeral counts and states;
do not interpolate them into title strings or write them into the layout.
Imperative registrations that need metadata before mounting provide it through
`getChromeForContext`; instance-owned chrome remains available through
`getChrome` after the view mounts.

Problems defaults to a grouped tree and exposes an upper-right action for its
compact Code/Message/File/Source table. Consumers may select the initial mode
with `defaultViewMode`, but the view choice remains transient and never changes
diagnostic ownership or workspace layout. Keep table overflow on the shared
shadcn Scroll Area rather than introducing a native panel scrollbar.

The compact search field owns the Problems severity-filter trigger. Present the
four severity gates as checkbox items in its shared Dropdown Menu so filtering
remains discoverable without consuming a toolbar control for every severity.
Keep this small menu untitled, wide enough for every severity label, and retain
the established semantic icon colours across registered and fallback icons.
Align totals in one fixed count column so changing label length cannot clip or
shift them. The table/tree and collapse-all actions remain independent toolbar
controls.

The Problems plugin contributes its live diagnostic total to the owning leaf
badge. The internal panel toolbar does not repeat that title count; resource
group counts retain the same shared Badge treatment.

The owning leaf also supplies the Problems title. Do not repeat it inside the
panel toolbar; keep the search field, filter trigger, presentation toggle, and
collapse action together at the toolbar's right edge.

Framework plugins should use `AppShellPlugin.createDiagnosticCollection()` so
their collection is disposed automatically. Collection `buildItemMenu` hooks
may append quick fixes, while primary row activation remains navigation-only.
Do not put callbacks on `WorkspaceDiagnostic` data or make the panel inspect
Lapis paths, vaults, or editor instances.

## Styling

Workspace components use colocated native CSS and public
`--ui-workspace-*` tokens. Override tokens on an ancestor. Do not pass Tailwind
utility strings to component props.

Controls painted on `--ui-workspace-panel` use
`--ui-workspace-panel-action-hover-background` and
`--ui-workspace-panel-action-hover-foreground`. Their defaults bind to the
host theme's `--sidebar-accent*` semantics so hover feedback stays distinct
from sidebar, status-bar, ribbon, and floating-window header surfaces.

Every registered Svelte or imperative view is painted by `WorkspaceViewHost`
through the public `--ui-workspace-view-background` and
`--ui-workspace-view-foreground` tokens. The companion
`--ui-workspace-view-secondary-background` token supplies a contrasting nested
surface. Body, bottom-panel, grouped-panel, mobile, floating, and standalone
views use workspace primary and secondary paint; only an ungrouped left/right
sidebar swaps the pair so its primary is the panel surface and its secondary is
the workspace surface. Consumers may override the view tokens for exceptional
content, but normal views should not implement their own placement selectors.

Desktop layout hosts also retain the stable `data-workspace-surface` contract:
`body`, `left-sidebar`, `right-sidebar`, and `bottom-panel`. Use these
identifiers for diagnostics and placement assertions instead of inspecting or
caching the controller parent graph. Moving a view changes its inherited
design-core surface styling without adding placement props to the view.

Trigger-based shadcn overlays follow the trigger's `ownerDocument`.
`WorkspacePopoutSurface` is an inline-overlay host, so Popover, Hover Card,
Tooltip, Dropdown Menu, Context Menu, and Select stay in the detached document
instead of escaping back to the opener. Do not add view-specific portal
targets or copy popup detection into consumer panels.

## Development status

The framework is being migrated from the standalone Lapis app-shell package.
See `src/shared/workspace/PLAN.md` for the audited slice matrix and
`src/shared/workspace/REFERENCE.md` for source provenance. The implementation,
interaction, and canonical-reference slices are complete; candidate Visual
Delta baselines remain pending manual approval.
